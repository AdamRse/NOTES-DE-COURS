Segmentation d’un projet multitier
Il est important de découper un projet informatique en blocs/couches/layers bien distincts
En informatique, le principe de séparation des responsabilités à cours à tous les niveaux : au sein des fonctions, au sein des classes et aussi des grands ensembles d’une application que l’on appelle Layer
Chaque Layer de plus haut niveau possède, son serveur ou son instance propre, l’objectif étant de séparer complètement ces layers, et de les modifier ou les faire s’échelonner de manière complètement autonomes

Architecture n-tiers
3 Layers, sur 3 serveurs/terminaux/docker différents
La couche Display/Présentation
La couche Business
La couche Base de données

Intérêts
Le segmentation permet une plus grande maintenabilité de la structure
Chaque couche peut être modifiée indépendamment sans crainte pour les autres
L’avantage majeure est la scalabilité du projet
L’architecture de chaque couche peut être modifiée pour s’adapter à un nouveau besoin
La puissance de chaque peut être modifiée indépendamment pour répondre à, par exemple, une augmentation de charge
La maintenance et la pérennité sont également facilités l'architecture ntier elle permet la mise en oeuvre de système plus complexe

Organiser sa couche Business
Dans le cas d’un projet Php Symfony ou Laravel, la couche business se situera sur le serveur du framework
L’objectif est clair : il faut, dans cette couche, différencier le code INFRASTRUCTURE liés aux décisions techniques, framework, et librairies tierces, le code de PRÉSENTATION, liés au vues, et le code MÉTIER, qui va contenir le coeur de votre application, la valeur ajoutée de celle-ci
Votre code métier doit être complète IMPERMÉABLE à toute les autres couche en utilisant les principes de la programmation SOLID
Il faut, in fine, pouvoir changer de Framework, ou d’ORM, sans avoir à changer un caractère de sa couche métier

Architecture Hexagonale du code Métier

Notion PORT - ADAPTATEUR
L’architecture hexagonale fonctionne selon le principe de port adaptateur
Il s’agit en réalité, d’une utilisation systématique du principe SOLID d’inversion de dépendance lorsque les classes MÉTIERS doivent utiliser des classes de l’INFRASTRUCTURE (comme des repositories, ou des clients http tels que guzzle ...)
Le principe est très simple
PORT = INTERFACE MÉTIER, se trouvant au sein du code métier
ADAPTATEUR = CLASSE INFRASTRUCTURE IMPLÉMENTANT L’INTERFACE se trouvant au sein du code infra

Use Case, Presenter et VueModel
Un projet Clean Architecture se pense en terme de UseCase
Concrètement, un UseCase est une Classe métier représentant une action de votre projet. Il s’agira de votre point d’entrée vers votre code métier, la classe UseCase prendra en paramètre une classe Request (simple Data Object) contenant les informations nécessaires au UseCase Et retournera un objet Response. Cet objet sera envoyé au Presenter qui crééra un ViewModel Qui sera envoyé à la vue 
Un use case est un scénario, par exemple : DisplayCartUseCase, RegisterCarUseCase ...
